3. SEMANTIC STRUCTURE-AWARE HIERARCHICAL RECURSIVE CHUNKING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  File : backend/api/rag/chunker.py
  Class: HierarchicalChunker

  ── 3.1  Core Idea ──────────────────────────────────────────────────────────

  Instead of blindly slicing text at fixed character counts, the chunker first
  UNDERSTANDS the document structure (heading hierarchy, tables, paragraphs)
  and then splits along semantic boundaries.

  ── 3.2  Heading Detection ──────────────────────────────────────────────────

  Level │ Markdown pattern   │ Legal document pattern
  ──────┼────────────────────┼──────────────────────────────────────────────
  H1    │ # Heading          │ CHAPTER X, PART X, TITLE X
  H2    │ ## Heading         │ SECTION X, ARTICLE X, § X, 1. ALL CAPS
  H3    │ ### Heading        │ 1.1 Clause, 1.1. Sub-clause, a) Item, (i) Item

  Priority: Markdown patterns checked first, legal patterns as fallback.
  This handles both markdown-formatted documents and raw PDF extractions.

  ── 3.3  Table Detection and Atomic Preservation ────────────────────────────

  Tables are extracted BEFORE structural parsing and kept as atomic chunks:

    Detected by:
      • Lines matching  ^│.+│$   (pipe-separated rows)
      • Lines matching  ^[-|+]{3,}$  (ASCII table borders)

    Tables are NEVER split. Each table = one chunk with heading "[Table]".
    After structural parsing, tables are re-injected into the chunk list.

  ── 3.4  Recursive Splitting Algorithm ──────────────────────────────────────

    parse_structure(document_text)
      → StructureNode tree (H1 → H2 → H3 → text)

    for each node in tree:
      if node.full_length() ≤ chunk_size:
          → emit as single chunk             ← ATOMIC LEAF
      elif node has H3 children:
          → recurse into H3 sub-nodes        ← STRUCTURAL SPLIT
      else:
          → sentence_split(text, chunk_size) ← SENTENCE FALLBACK

    sentence_split uses NLTK punkt tokenizer with configurable overlap:
      • Default chunk_size  : 800 characters
      • Default overlap     : 150 characters
      • Min chunk size      : 80 characters (below this, chunk is discarded)

  ── 3.5  Chunk Metadata ─────────────────────────────────────────────────────

  Every chunk carries:
    • text         — raw chunk content
    • heading      — immediate section heading
    • section_path — full breadcrumb, e.g. "Contract > Section 2 > 2.1 Payment"
    • ord          — sequential position within document
    • node_type    — "text" or "table"
    • document_id, title, jurisdiction, year, source

  The section_path is stored in ChromaDB and used for citations.

  ── 3.6  Why This Matters ───────────────────────────────────────────────────

  Traditional fixed-size chunkers break mid-sentence or mid-table, losing
  context. This chunker ensures:
    • A clause is never split from its section heading
    • Table cells are never orphaned
    • Retrieval results carry full provenance for citations

5. HYBRID RETRIEVAL — BM25 + VECTOR SEARCH + RECIPROCAL RANK FUSION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  File : backend/api/rag/chroma_store.py  →  ChromaHybridStore.search()
  File : backend/api/rag/retrieval.py     →  RetrievalService.retrieve()

  ── 5.1  BM25 Search ────────────────────────────────────────────────────────

    Library   : rank_bm25 >= 0.2.2  (BM25Okapi variant)
    Index     : In-memory, built from all chunk texts at startup
    Tokenizer : Whitespace split, lowercased

    BM25Okapi scoring formula:
      score(q, d) = Σ IDF(qᵢ) · [f(qᵢ,d)·(k₁+1)] / [f(qᵢ,d) + k₁·(1-b+b·|d|/avgdl)]

      where:
        f(qᵢ,d) = term frequency of query term qᵢ in document d
        |d|     = document length
        avgdl   = average document length in corpus
        k₁ = 1.5  (term frequency saturation)
        b  = 0.75 (length normalization)

    BM25 excels at: exact keyword matching, legal jargon, case names, statutes

  ── 5.2  Vector Search ──────────────────────────────────────────────────────

    Embedding model : all-MiniLM-L6-v2  (local, 384-dim)
    Index type      : HNSW (Hierarchical Navigable Small World graph) via Chroma
    Similarity      : Cosine similarity on L2-normalized vectors
    Query flow      : encode(query_text) → 384-dim vector → Chroma.query()

    Vector search excels at: semantic similarity, paraphrasing, concept matching

  ── 5.3  Reciprocal Rank Fusion (RRF) ───────────────────────────────────────

    RRF merges the BM25 ranked list and the vector ranked list into a single
    fused ranking without requiring score normalization.

    Formula:
      RRF_score(doc) = Σ  1 / (k + rank(doc, list_i) + 1)
                      lists

      where k = 60  (smoothing constant, standard value from RRF paper)

    Example (k=60):
      Rank 1  →  1/(60+1+1) = 0.01613
      Rank 5  →  1/(60+5+1) = 0.01515
      Rank 50 →  1/(60+50+1) = 0.00901

    A document ranked #1 in BM25 and #3 in vector gets:
      score = 1/62 + 1/64 = 0.01613 + 0.01563 = 0.03176

    A document ranked #1 in only BM25 gets:
      score = 1/62 = 0.01613

    This naturally rewards documents that appear highly in BOTH lists.

    Implementation:
      _rrf(ranked_lists=[bm25_ids, vector_ids], k=60)
        → dict: {chunk_id: fused_score}
        → sorted descending by score
        → top-k chunk ids fetched from Chroma for full metadata

  ── 5.4  Filter Application ──────────────────────────────────────────────────

    Chroma WHERE filters applied to vector search (pre-retrieval)
    Keyword include/exclude filters applied post-retrieval (Python)
    candidate_k = min(k × 4, total_chunks)  — over-fetch for filter headroom

  ── 5.5  Full Retrieval Call ─────────────────────────────────────────────────

    RetrievalService.retrieve(query, k=8, filters)
      1. encode(query)          → 384-dim query vector
      2. _vector_search(...)    → ordered list of chunk_ids  (cosine)
      3. _bm25_search(...)      → ordered list of chunk_ids  (BM25Okapi)
      4. _rrf([bm25, vector])   → fused ranked list
      5. fetch top-k from Chroma with full metadata
      6. return formatted chunk list with score, text, heading, section_path, citations

  ── 5.6  Why Hybrid > Pure Vector ───────────────────────────────────────────

    Pure vector search misses exact case citations: "Donoghue v Stevenson"
    Pure BM25 misses semantic matches: "duty of care" ≠ "responsibility to consumers"
    Hybrid + RRF captures both — documented 10-20% NDCG improvement in literature

    ─────────────┼─────────┼──────────────────────────────────────────────
    temperature  │ 0.7     │ Sampling randomness (0=deterministic, 2=wild)

    top_k        │ 50      │ Top-k token candidates per step
    num_predict  │ 2048+   │ Max tokens to generate (see note below)

  ── 7.2  Gemma 4 Thinking Tokens — Important Quirk ─────────────────────────

    Gemma 4 uses an internal chain-of-thought mechanism. On longer legal
    prompts, it generates "thinking" tokens internally before producing the
    visible response. These thinking tokens count toward num_predict.

    Bug observed in Ollama 0.23.2: when num_predict < 1024 on prompts > 200
    tokens, all generation budget is consumed by internal reasoning and the
    content field returns empty ("").

    Fix applied: enforce  num_predict = max(requested, 2048)
    This guarantees enough budget for both reasoning AND the visible response.

  ── 7.3  Streaming Strategy ─────────────────────────────────────────────────

    Ollama 0.23.2 streaming via /api/chat does not emit content tokens for
    gemma4 when a system message is present (known upstream bug).

    Workaround: "Simulated streaming"
      1. Full non-streaming inference → complete response text
      2. Split text by whitespace with re.split(r'(\s+)', text)
      3. Yield each word/token via Django StreamingHttpResponse (SSE)
      4. Frontend receives real-time token events and appends to message

    This gives the user a genuine typewriter experience without actually
    streaming from the model. Latency = full inference time, then instant
    word delivery.

8. INFERENCE MODES & PROMPT ENGINEERING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  File : backend/api/inference/prompts.py

  ── Mode A — Document Summarizer ────────────────────────────────────────────

    Input : uploaded document text + title
    Prompt: system instructs IRAC-style Markdown summary with 4 sections:
              ## Executive Summary  (2-3 bullets)
              ## Key Points         (4-6 bullets)
              ## Risks              (identified legal risks)
              ## Obligations        (key obligations and deadlines)
    Rule  : every bullet MUST include citation [Section X, paragraph Y]
    Output: raw Markdown

  ── Mode B — Clause Detection & Classification ──────────────────────────────

    Input : contract text + title
    Clause types searched (10 default):
      Termination, Indemnity, Confidentiality, Intellectual Property,
      Liability Caps, Governing Law, Payment Terms, Warranties,
      Force Majeure, Assignment
    Output format per clause:
      **Clause Type:** <type>
      **Citation:** <nearest section header>
      **Confidence:** high | medium | low
      **Excerpt:** <verbatim text>

  ── Mode C — Case-Law IRAC Q&A (RAG-powered) ────────────────────────────────

    Input : user question + top-k retrieved chunks from hybrid search
    Format: IRAC (Issue / Rule / Application / Conclusion)
    Citation rule: every claim must be cited as [Case Name, Year] or [Source N]
    Fallback: "Insufficient basis from provided sources" if context is empty
    Output: structured Markdown with IRAC headings

  ── Post-Processing ─────────────────────────────────────────────────────────

    File  : backend/api/inference/post_processor.py
    Class : ResponseProcessor

    • Extracts all [citation] references via regex
    • Parses IRAC sections (Issue/Rule/Application/Conclusion) from Markdown
    • Computes citation coverage = sentences_with_citations / total_sentences
    • Appends legal disclaimer to all responses

10. VUE 3 FRONTEND
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Framework  : Vue 3 (Composition API) + Vite
  State      : Pinia stores (auth, chat, documents, history)
  Routing    : Vue Router 4
  UI kit     : Bootstrap 5 + Bootstrap Icons
  HTTP       : Axios (API calls) + native fetch (SSE streaming)

  ── Views ────────────────────────────────────────────────────────────────────

    LoginView      → JWT login form
    RegisterView   → User registration
    ChatView       → Main chat interface (sidebar + message area)
    DocumentsView  → Upload and manage legal documents
    HistoryView    → Browse and search past conversations
    SettingsView   → Inference settings (temperature, tokens, etc.)

  ── Chat Streaming (SSE) ─────────────────────────────────────────────────────

    chatAPI.sendMessageStream(payload, { onToken, onDone, onError })
      → fetch POST /api/v1/chat  (stream: true)
      → ReadableStream reader
      → line-by-line SSE parsing: "data: {json}\n\n"
      → onToken(token)  called per word chunk
      → onDone(chunk)   called on {type: "done"}
      → onError(msg)    called on {type: "error"}

    Chat store (Pinia):
      • Appends placeholder assistant message immediately
      • Accumulates tokens in message.content in real time
      • Sets message.streaming = false on done
      • Auto-scrolls chat area on every token

  ── ChatMessage.vue — Inline Markdown Renderer ──────────────────────────────

    Renders headings (h1–h4), bold, italic, unordered/ordered lists,
    inline code, blockquotes, horizontal rules, and citation references.

    Citation refs like [Case Name, Year] or [Section X] are styled as
    highlighted <cite> badges (blue background) for visual clarity.

    Streaming state shows animated bouncing dots (CSS keyframe animation).

11. SECURITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  • JWT access tokens (1h TTL) + rotating refresh tokens (7d TTL)
  • Rate limiting: 60 chat requests per user per hour (Redis-backed)
  • SHA-256 document deduplication (prevents storing duplicate files)
  • Audit log for all uploads, ingestions, chat requests
  • CORS restricted to http://localhost:5173
  • All document access scoped to owning user (Document.objects.get(user=request.user))
  • Passwords validated by Django's built-in validators
  • Legal disclaimer appended to every response
